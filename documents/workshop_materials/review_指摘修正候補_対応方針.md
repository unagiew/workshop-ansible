# 「Terraform_Ansible_勉強会_指摘修正候補.md」への対応方針

`documents/workshop_materials/Terraform_Ansible_勉強会_指摘修正候補.md` で指摘された各項目について、現状の001〜005の記述・実ファイル（`ansible/`・`terraform/`）と突き合わせたうえで、対応すべきかどうかの意見をまとめる。

凡例：**採用** = 内容に同意し反映すべき／**一部採用** = 方向性には同意するが範囲・表現を調整すべき／**見送り** = 現時点では対応しない（理由付き）。すでに現行資料や本セッションの変更で対応済みの項目は「対応済み」と明記する。

## 2. 最優先で追加・修正したい項目

### 2.1 「今回作るもの」を冒頭に追加

**意見：一部採用**

001 1.1にはすでに同趣旨のテキスト図がある。ゼロから追加するのではなく、既存の図を指摘候補のシンプルな版に寄せて読みやすくする程度で十分。大きな構成変更は不要。

### 2.2 「用語一覧」を序盤に追加

**意見：採用**

現状001〜002には用語集に相当するものがなく、初出時にその都度説明する形になっている。若手向けであることを踏まえると、001 1.2の直後に簡易な用語一覧表を置く価値は高い。ただし全13語を並べると初見の情報量が多いため、最初は主要語（VM/Terraform/Ansible/Inventory/Playbook/Module程度）に絞り、Controller/Managed Node等は5章側の用語一覧として分割するのが妥当。

## 3. Terraform周辺の修正候補

### 3.1 Terraform/cloud-init/Ansibleの役割説明の断定表現

**意見：採用（優先度高）**

001 3.2に実際に「実務においては...ベストプラクティスとされる」という断定表現が残っている。指摘の通り言い過ぎであり、「理解しやすい設計パターンの一つである」程度の表現に弱める修正は妥当。

### 3.2 Terraform Providerの説明を追加

**意見：一部採用**

003 7.2の`terraform`ブロック解説にすでに「プロバイダを介してTerraformからMultipassのVM作成・削除を行えるようになる」という説明文はある。指摘の簡易図（Terraform→Provider→Multipass→VM）を7.1か7.2に足すのは軽微な改善であり採用してよいが、テキスト説明自体は大きく変える必要はない。

### 3.3 terraform init/plan/apply/destroy

**意見：一部採用**

003 7.1にmermaidフロー図、9.2に実際の実行ログ例がすでにある。指摘の一覧表を丸ごと追加する必要はないが、「`plan`はいきなり変更せず差分を確認する安全確認である」という一文を7.1か9.2に足すのは有用。

### 3.4 Terraform Stateを独立して説明

**意見：一部採用（優先度中）**

現状`terraform.tfstate`への言及は`.gitignore`対象という程度で、内容の説明はない。指摘の図とセットで8章あたりに独立した小節を設けると理解が深まるが、今回の検証用途では「なぜstateが必要か」まで踏み込むと時間を取られやすい。時間配分次第で採否を判断してよい部類。

### 3.5 variables.tf / terraform.tfvars / main.tfの関係図

**意見：一部採用**

003 7.2〜7.4にすでにコード例・表による説明があり、指摘のサンプルとほぼ同じ内容が実装済み。不足しているのは「3ファイルの関係を1枚で示す図」のみなので、その図だけを7.3の冒頭に追加すれば十分。

### 3.6 terraform.tfvarsの説明修正

**意見：見送り**

現状003 7.4の「`terraform.tfvars`は各自の環境に依存する情報を含むためバージョン管理には含めない」は、実際の`.gitignore`設定（`terraform.tfvars`除外＋`terraform.tfvars.example`を用意）と一致しており、今回の教材では常に除外する運用で問題ない。指摘の「秘密情報が含まれる場合は除外する」という一般化された表現に変えると、逆に初学者には「今回は除外しなくてよいのか」という余計な判断を生む。現状の断定表現のままでよい。

### 3.7 for_eachの説明を強化

**意見：採用**

003 7.2に`for_each = var.nodes`の説明文はあるが、指摘の図（`ubuntu1 → multipass_instance.node["ubuntu1"]`）と`each.key`/`each.value`の対応表はない。追加コストが小さく理解の助けになるため、7.2に追記する。

## 5. Ansible周辺の修正候補

### 5.1 Controller / Managed Nodeを正式に説明

**意見：一部採用**

現状004にControllerやManaged Nodeという用語自体は明示的に出てこない（Inventory/Playbook/Moduleの3要素表のみ）。用語として導入する価値はあるが、11.1の説明とほぼ同じ内容の図を並べると冗長になるため、11.1の3要素表に「Controller＝Mac」「Managed Node＝ubuntu1/ubuntu2」という対応列を1つ足す程度に留めるのが妥当。

### 5.2 Inventory / Playbook / Module / Variablesの4分類

**意見：採用**

004 11.1はInventory/Playbook/Moduleの3要素構成になっている。今回追加した`template`サンプル（15.5）で「Playbookの`vars:`やInventoryのホスト変数」というVariablesの概念をすでに扱っているため、11.1の説明に4つ目の要素として`Variables`を追加すると、15.5への繋がりが自然になる。

### 5.3 ansible.builtin.ping

**意見：見送り（対応済み）**

004 13.1にすでに「ICMPのpingとは異なる」という説明があり、指摘内容とほぼ同じ趣旨がすでに反映されている。追加修正は不要。

## 6. Shell / scriptの説明で注意したい点

### 6.1 「MacのShellをリモート実行」という表現の修正

**意見：見送り（現状で妥当）**

004 15.1はすでに「Ansibleを実行しているMac上のスクリプトを対象ホストへ転送して実行できる」という表現であり、「スクリプトの実行場所」と「ファイルの所在」を混同させる書き方にはなっていない。指摘が懸念する誤解は現状の文面では生じにくいため修正不要。

### 6.2 Ansible = Shell実行ツールにならないようにする

**意見：一部採用**

`script`/`command`/`shell`の比較（17章）はすでにあり、今回のセッションで`template`も表に追加済み。ただし「AnsibleはSSHでコマンドを投げるだけのツールではない」という強めのメッセージ文自体は本文にないため、17章の冒頭か末尾に一文加えると指摘の狙いに合う。`apt`/`service`などの紹介は7章の演習（後述10.）とセットで検討する。

## 7. 冪等性を「説明」だけでなく「体験」させる

**意見：採用（優先度高）**

現状004で冪等性という言葉自体は11.1に登場するが、実際に「1回目changed→2回目changed=0」を手を動かして確認する演習はまだない。`script`モジュールは`creates`指定がない限り常に`changed`になる非冪等な例であり、逆にこれが良い対比教材になる。指摘の`apt` moduleの例（nginxインストール）はVMがインターネットに到達できる環境が前提になるため、ワークショップ実施環境（Multipassのネットワーク設定）を確認したうえで、22章の演習に「Level 3」的な位置づけで追加するのが現実的（10.・11.の項目と合わせて後述）。

## 8. トラブルシューティングの構成

**意見：見送り（対応済み）**

`review_004_ansible.md`での再構成により、Multipass→VM→SSH→Ansible ping→Playbookのレイヤー切り分けはすでに004 19〜21章として実装済み（早見表・切り分けフロー図含む）。指摘の構成と同等であり、追加の変更は不要。

## 9. 失敗させる演習を追加

**意見：一部採用**

- 失敗4（`{{ role }}`が未定義→`role is undefined`）は、本セッションで追加した004 15.5.5で既に実装済み（対応済み）。
- 失敗1（SSH鍵を間違える）・失敗2（InventoryのIPを間違える）・失敗3（`hosts`を間違える）は、004 19〜21章の一般的な切り分け説明はあるが、「実際に間違えたPlaybook/Inventoryを用意して意図的に失敗させる」演習形式にはなっていない。22章の演習に、意図的な失敗→原因特定という形式で1〜2個追加する価値はある。ただし全4種を一度に追加すると演習が重くなるため、失敗2（Inventory IP誤り）程度に絞るのが妥当。

## 10. 演習をLevel 1〜3に分ける

**意見：一部採用**

現状22章の演習1〜3（VM3台化・Shell変更・Ansible対象変更）は指摘のLevel 1〜2に近い内容をすでに満たしている。Level 3（`copy` moduleで自作Playbook、2回実行してchanged=0を確認）は現状ない。7.の冪等性演習と統合し、22章に「演習4：自分でPlaybookを作成する（`copy` module、冪等性確認）」を追加するのがよい。既存演習の構成自体を作り直す必要はない。

## 11. 最終自由課題を追加

**意見：一部採用（範囲は絞る）**

- `template` moduleでVMごとに異なる設定ファイルを生成する課題は、本セッションで追加した15.5がすでにこれに相当する内容を演習前に体験できる形で実装済み。
- nginxインストール・起動、VM3台化は、22章の演習1と重複する部分がある／ネットワーク接続とapt実行時間が前提になるため、必須の演習ではなく任意課題として案内する程度に留めるのが無難。`terraform destroy`→`apply`→Ansible再実行で同じ結果になることを確認する締めくくりは、9.5（VMの削除）と組み合わせて軽く触れる価値がある。

## 15. 講師目線での最終方針

**意見：採用（方向性のみ）**

「知識→仕組み理解→実際に動かす→わざと変更する→失敗させる→切り分ける→自分で自動化する」という軸、および「Terraform=VMを用意する／cloud-init=土台を作る／SSH=つなぐ／Ansible=自動化する」という4分割メッセージには同意する。ただし資料を大幅に作り直す必要はないという方針通り、今回の対応も新規追加は7.・9.（一部）・10.（一部）・12.の演習系に絞り、既存の章立て・図をベースに小さな追記で対応するのが妥当。
