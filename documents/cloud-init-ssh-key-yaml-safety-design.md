# Design Note: Safe YAML Interpolation of `ssh_public_key` in `cloud-init.yaml.tftpl`

## 1. Goal / Problem Statement

### Current State

`terraform/main.tf` reads the user's SSH public key file and trims only the
outer whitespace of the whole file:

```hcl
locals {
  ssh_public_key = trimspace(
    file(pathexpand(var.ssh_public_key_path))
  )
}
```

This value is passed untouched into `templatefile()` for
`terraform/cloud-init.yaml.tftpl`, where it is interpolated as an **unquoted
YAML plain scalar** inside a list item:

```yaml
    ssh_authorized_keys:
      - ${ssh_public_key}
```

An SSH public key has the shape `<type> <base64> [comment]`. The `[comment]`
is free text that OpenSSH never validates and that many key-generation flows
default to `user@host`, but which a user can set to anything (it is commonly
hand-edited, copy-pasted from elsewhere, or generated by tools with unusual
defaults). Because the interpolation happens into a YAML **plain scalar**
context, the following inputs are unsafe:

- A colon followed by a space (`: `) anywhere in the string — YAML would
  parse it as a mapping key/value separator, corrupting the document
  structure.
- A comment (or, in principle, the whole line) starting with a YAML
  indicator character: `* & ! % @` `` ` `` `# ' "` `| > [ ] { }` `-` (when
  followed by a space) — YAML would interpret the line as an anchor,
  tag, alias, comment-start, flow collection, etc., instead of literal text.
- Embedded newlines/blank lines — would break the single list item into
  multiple malformed YAML lines.
- Leading/trailing whitespace on the *value itself* beyond what
  `trimspace()` removes — `trimspace()` only trims the outer edges of the
  entire file content, not, e.g., a stray blank line or trailing `\r` in the
  interior, or multiple keys accidentally left in the file.

The failure surfaces either as a `terraform apply`-time error (if the
`todoroff/multipass` provider validates the cloud-init document client-side
before sending it to the daemon) or as a cloud-init failure inside the VM at
first boot (invalid `#cloud-config` YAML is silently skipped or partially
applied by cloud-init, depending on version) — in both cases the actual root
cause (an unsafely interpolated string) is several layers removed from the
symptom, making it hard to diagnose.

### Target State

- The rendered cloud-init document is valid YAML for any syntactically valid
  SSH public key content, regardless of what the comment field contains.
- Invalid/malformed key file content (e.g. wrong number of fields, non-base64
  key material, multiple keys in the file) is rejected at `terraform plan`
  time with a clear, actionable error message — not discovered later as a
  cloud-init boot failure or an opaque provider error.
- The fix does not change the deployed `ansible` user's authorized key
  (i.e. the same key continues to authenticate).

### Out of Scope

- Supporting multiple SSH public keys per node (the current design assumes
  exactly one key path via `var.ssh_public_key_path`; this note does not
  extend that).
- Changes to `inventory.ini.tpl` or other templates — this note is scoped to
  `cloud-init.yaml.tftpl` and the `ssh_public_key` local in `main.tf`.
- The unrelated hygiene items already covered by
  `documents/terraform-main-improvements-design.md` (provider pinning,
  `.gitignore`, tfvars split, etc.) — not revisited here except where they
  intersect (they don't).

## 2. Affected Components & Architecture Diagram

Two files, one data flow:

```
var.ssh_public_key_path (tfvars)
        |
        v
file() + trimspace()  --------------------->  local.ssh_public_key   (main.tf)
        |                                              |
        |                                              v
        |                                   templatefile(cloud-init.yaml.tftpl, {...})
        |                                              |
        |                                              v
        |                                   multipass_instance.node.cloud_init
        |                                              |
        v                                              v
  (no validation today)                    multipass provider -> multipass daemon -> VM boot
                                              (client-side validation, if any)   (cloud-init parses YAML)
```

No architecture diagram beyond this is needed; the change is local to how one
string is produced and how it is embedded into one template.

## 3. Proposed Changes & Implementation Plan

### Recommendation: combine approaches 1 + 3, and strip the key comment

Use `yamlencode()` to build the cloud-init document as an HCL data structure
(approach 1), add a `precondition` that validates the key format and rejects
unsafe content fail-fast (approach 3), and strip the comment field down to
`<type> <base64>` only (the "also consider" question) before it ever reaches
YAML. Approach 2 (manual quoting + `replace()` escaping) is not recommended
as the primary fix — see trade-off discussion below — but is noted as a
fallback if `yamlencode()` turns out to be undesirable for other reasons.

#### Why `yamlencode()` (approach 1) over manual quoting (approach 2)

- `yamlencode()` is a Terraform built-in that emits well-formed YAML from an
  HCL value by construction — it treats `ssh_authorized_keys` as an HCL list
  of strings and lets Terraform decide the correct YAML scalar style
  (quoted, block, whatever is safe) for *whatever* string ends up in it. This
  is correct for every input, not just the inputs the author thought to
  escape.
- Approach 2 requires manually reasoning about every YAML-unsafe construct
  (colon-space, leading indicators, embedded newlines, trailing whitespace,
  unicode edge cases) and hand-writing the exact escaping rules for a
  double-quoted YAML scalar (`\` → `\\`, `"` → `\"`, plus in principle
  control characters like literal newlines would need `\n` escapes that
  `replace()` alone does not conveniently produce). This is a hand-rolled
  mini YAML-encoder living in HCL `replace()` calls — easy to get subtly
  wrong, and any future field added to the cloud-init template would need
  the same treatment repeated ad hoc. `yamlencode()` solves this class of
  bug once, for the whole document, permanently.
- The `.tftpl` approach is not inherently bad for cloud-init in general, but
  this specific document is only two dynamic pieces (the `ansible` user
  block and the static `packages` list) — small enough that restructuring it
  as HCL is a modest, self-contained change, not a rewrite of a large
  template.

**Trade-off accepted:** `cloud-init.yaml.tftpl` stops being a directly
readable YAML file for this section and becomes an HCL map/list rendered by
`yamlencode()`. Anyone editing the cloud-init shape in the future edits HCL
instead of YAML directly. This is a one-time readability cost in exchange for
eliminating an entire class of injection bug.

#### Why also add a precondition (approach 3), on top of `yamlencode()`

`yamlencode()` guarantees the output is *syntactically valid YAML*. It does
**not** guarantee the *content* is a syntactically valid SSH public key. A
typo'd key path pointing at the wrong file (e.g. a private key, an
`.ssh/config` fragment, or an empty file) would still render into "valid
YAML that is a useless or dangerous cloud-init entry," and the failure would
only surface as an SSH authentication failure post-boot — just as hard to
diagnose as the original bug, only later in the pipeline. A `precondition`
on the key format catches this at `terraform plan`/`apply` time with a
message that points directly at the cause.

This mirrors the existing convention already in `variables.tf`, which uses
`validation` blocks for `nodes`, `memory`, and `disk`. Since
`ssh_public_key` is derived in a `locals` block (not a plain input variable),
the equivalent mechanism is a `precondition` inside a `lifecycle` block on
the resource that consumes it, or (cleaner, and reusable) a `check` block —
Terraform does not support `validation` on `locals` directly. This note
recommends a `check` block scoped to the key format, since it runs
independently of resource apply ordering and produces a clear, dedicated
warning/error without being tied to `multipass_instance.node`'s own
lifecycle.

#### Why strip the comment (recommended: yes)

The comment field (`user@host` or arbitrary text) has no function in
`authorized_keys` — OpenSSH ignores it entirely for authentication purposes.
It is also the single largest source of unpredictable, user-edited content
in this value (the `<type>` and `<base64>` fields are machine-generated and
already safe: base64 alphabet is `[A-Za-z0-9+/=]`, key types are a small
known set). Stripping the comment down to `<type> <base64>`:

- Removes the highest-risk portion of the string, in addition to (not
  instead of) the `yamlencode()` fix — defense in depth costs nothing here.
- Makes the `precondition` regex simpler and stricter (no need to allow
  "anything after the base64 field").
- Has no functional downside: the deployed key still authenticates
  identically; only a comment used purely for human bookkeeping is dropped
  from the *rendered cloud-init*, not from the user's own key file on disk.

Recommendation: extract `<type>` and `<base64>` via `regex()` in
`locals`, discard the rest, and validate the two extracted fields directly.

### Implementation Plan

1. **`terraform/main.tf` — parse and re-derive `ssh_public_key`:**
   - Read the file and `trimspace()` as today.
   - Add a `regex()` extraction of `^(ssh-[a-z0-9-]+|ecdsa-[a-z0-9-@]+) +([A-Za-z0-9+/=]+)` (exact character class/type list to be confirmed against supported key types: `ssh-ed25519`, `ssh-rsa`, `ecdsa-sha2-*`) to pull out `key_type` and `key_material`, ignoring anything after (i.e. dropping the comment).
   - Reconstruct `local.ssh_public_key = "${key_type} ${key_material}"` — this is the value passed to the template, now guaranteed to be exactly two fields.
2. **`terraform/main.tf` — add a `check` block:**
   - `condition` asserts the original file content matched the expected regex (i.e. `can(regex(...))` succeeded).
   - `error_message` explains the expected `<type> <base64> [comment]` format and names the offending file path (`var.ssh_public_key_path`), so the user can fix their key file directly.
3. **`terraform/cloud-init.yaml.tftpl` → restructure via `yamlencode()`:**
   - Two options, both acceptable; recommend (a) for minimal blast radius:
     - (a) Keep the static parts of `cloud-init.yaml.tftpl` as a `.tftpl` "shell," but replace the `ssh_authorized_keys` list rendering so that the *entire* `users` block (or at minimum the `ansible` user entry) is produced by `yamlencode()` in `main.tf` and passed into the template as a pre-rendered YAML fragment string — this keeps the packages list and top-level cloud-config keys as plain YAML, changing only the risky section.
     - (b) Fully replace `cloud-init.yaml.tftpl` with a single `yamlencode({...})` call in `main.tf` that builds the whole cloud-config document (`users`, `ssh_pwauth`, `disable_root`, `packages`) as one HCL map, and drop the `.tftpl` file and `templatefile()` call entirely, passing the `yamlencode()` result straight to `cloud_init`.
   - Recommendation: **(b)** — the whole file is small and entirely static except for the one field; collapsing it to a single HCL map removes the templatefile layer entirely and is easier to review than a half-YAML/half-HCL hybrid. The `#cloud-config` shebang line must be preserved by prepending it as a literal string before the `yamlencode()` output, since `yamlencode()` only emits the YAML body, not the leading `#cloud-config` marker cloud-init requires.
4. **Confirm output shape:** `yamlencode()` produces block-style YAML by default; verify (via `terraform console` or `terraform plan` with a throwaway key value containing `: ` and a leading `@`) that the rendered `ssh_authorized_keys` entry is a properly quoted/escaped scalar and that cloud-init accepts the resulting document.
5. **No changes needed to `terraform/variables.tf`** — `var.ssh_public_key_path` itself is unaffected; only how its contents are processed changes.

## 4. Risks & Mitigation

| Risk | Mitigation |
|---|---|
| `yamlencode()` output differs subtly from the hand-written YAML (indentation, key ordering, list style) and existing running VMs get an unwanted `cloud_init` diff on next `apply`, potentially triggering unwanted recreation. | Multipass instances typically only apply `cloud_init` at first boot; confirm via `terraform plan` on existing state whether the provider treats `cloud_init` as `ForceNew`. If so, this is expected and desired (the fix must apply to new VMs at least); document this as a one-time recreation for existing nodes in the note's validation step, not a silent risk. |
| The comment-stripping regex is too strict and rejects a valid key type not in the initial list (e.g. `sk-ssh-ed25519@openssh.com` for FIDO2 keys). | Enumerate supported types explicitly from OpenSSH's own `ssh-keygen` output format, and keep the `check` block's error message explicit about which types are supported so the user can report a gap rather than silently fail. |
| A `check` block is a relatively new Terraform feature (1.5+); repo already requires `>= 1.6.0` in `terraform { required_version }`, so no compatibility gap — but confirm the `todoroff/multipass` provider and any CI pinning don't lag behind. | Verify `required_version` in `terraform/main.tf` (already `>= 1.6.0`) covers `check` blocks (available since 1.5.0) — no action needed beyond confirming this during implementation. |
| Dropping the comment from the rendered cloud-init could surprise a user who greps the running VM's `authorized_keys` expecting to see their `user@host` comment for bookkeeping. | Call this out explicitly in the design note (done here) and, if desired, mention it in a code comment in `main.tf` next to the regex extraction, so the behavior is documented at the point of change, not a silent side effect. |
| Restructuring `cloud-init.yaml.tftpl` into `main.tf` (option 4b) changes where future contributors go to edit cloud-init content, which could reduce discoverability. | Add a short comment at the top of the `yamlencode()` block in `main.tf` noting that this replaces the old `cloud-init.yaml.tftpl`, and mention the change in the PR/commit description; `doc-writer` should be used afterward if any README/setup doc references the `.tftpl` file by name. |

## 5. Validation & Test Plan

Since this changes provisioning behavior (not authentication/authorization
directly, but security-adjacent — malformed SSH key handling), validation
must cover both the "malicious/malformed input rejected early" path and the
"normal input still works" path, per the repo's testing standards.

1. **Precondition rejects malformed key file** — `terraform plan` with
   `var.ssh_public_key_path` pointing at a file containing only
   `not-a-valid-key` → expect `plan` to fail with the `check` block's
   explicit error message, not a generic Terraform type error.
2. **Precondition rejects a key with an unsafe comment, confirming the
   comment is irrelevant to acceptance** — a file containing
   `ssh-ed25519 AAAA...validbase64... user: with a colon` → expect `plan`
   to succeed (since only `<type>` and `<base64>` are validated/used) and
   the comment to be silently dropped from the rendered cloud-init.
3. **Rendered YAML is valid for a comment containing every documented
   unsafe construct** — construct a test key file with comment
   `*bad: yes! @nope #comment 'quote' "dquote"` and confirm (a) the
   `ssh_authorized_keys` line in the previous behavior would have broken
   YAML (document this as the "before" repro), and (b) with the fix, the
   comment is stripped before reaching YAML at all, so the construct never
   appears in the output — the strongest form of mitigation.
4. **End-to-end: `terraform apply` succeeds and the `ansible` user can
   authenticate** — run `terraform apply` with a real key pair whose
   comment is deliberately set to `it's: a "tricky" one!`, confirm VM boots,
   and confirm `ssh ansible@<node-ip> -i <private_key>` succeeds — this is
   the closest analogue to a 401/403-style check available here (the
   equivalent "unauthorized" case is: confirm a *different* private key,
   not matching the deployed public key, is refused by the VM's SSH daemon,
   proving the key was installed correctly and not corrupted into an
   always-accept or always-reject state by malformed YAML).
5. **Regression: normal key with a typical comment still works** — a
   standard `ssh-keygen`-generated key with comment `user@laptop` → `plan`
   and `apply` succeed with no behavior change from before the fix.
6. **`terraform fmt` and `terraform validate`** are run clean on
   `terraform/main.tf` after the change, per repo convention (`cargo fmt`
   equivalent for this stack).

Suggested next owner: `plan-driven-coder`, after this design is approved,
followed by `qa-test-verifier` to execute the scenarios above (especially
scenario 4's authentication check, since it borders on
auth-adjacent/permission behavior per this repo's testing rules), then
`doc-writer` only if any existing documentation references
`cloud-init.yaml.tftpl` by name/path and needs updating to reflect its
removal (implementation plan option 4b) or restructuring (option 4a).

## 6. Addendum: `check` block replaced with `lifecycle.precondition`

QA review found that a `check "ssh_public_key_format"` block is
**advisory-only**: Terraform prints its `error_message` as a warning, but
`terraform plan`/`apply` still completes with exit code 0. In this design's
context, that means an `apply` with a malformed key file would proceed and
silently create a `multipass_instance.node` with an empty
`ssh_authorized_keys` entry — an unreachable VM — rather than being stopped,
defeating the "reject at plan time" goal stated in Section 1.

Fix: the `check` block was removed and replaced with a `lifecycle {
precondition { ... } }` block on `resource "multipass_instance" "node"`,
asserting the same `local.ssh_public_key_match != null` condition with the
same error message. A `precondition` failure is a hard error: `plan`/`apply`
stop with a non-zero exit code before the resource is created.

The `check` block was not kept alongside the precondition — both would
assert the identical condition, so keeping both would be duplicate
validation of the same fact without adding coverage. The precondition alone
satisfies both requirements from Section 1 (clear, actionable message; hard
failure at plan time).
